# G2 2.3.0 CFW compatibility audit

Stock G2 **2.3.0.24** and R1 **2.3.0.0005** were fetched from the Even Realities CDN on 2026-09-15. Both firmware-check endpoints agree on the release metadata. Downloads match the vendor MD5 and byte counts; the archive and application additionally pin SHA-256. See `2.3.0-vendor-check.json` for vendor responses.

## Build decision

**Do not apply the 2.2.10 CFW profile to 2.3.0.** All 24 reviewed hook signatures fail at their existing addresses. Of 123 address entries with byte signatures, 121 differ. The main payload grows by 44,836 bytes and its bundle payload offset moves from 779,181 to 779,243. The codec, BLE controller, touch and case components are unchanged; the bootloader and Apollo main change.

The latest fetched `jimrandomh/g2flash` main is `d968c2ccbafb85a91d1dc4683eee77accfad3142`, already used by the current 2.2.10.72 CFW. Its native base is still 2.2.9.22. Fetching upstream therefore does not supply a 2.3.0 address profile. No 2.3.0 CFW was generated or added to the release catalog.

## RAM and remaining work

Matched literal loads suggest that the framebuffer pointer moves from `0x200008b4` to `0x200008b8`; the primary heap arena moves from `0x202728a8` to `0x2027299c`; the settings block moves from `0x20074c90` to `0x20075e08`. These different deltas rule out a blanket offset replacement. The font-root matching is ambiguous (`0x20077a54` versus `0x20077a58`). Heap-tail reservation addresses must be derived again from verified arena bounds.

A rebase still requires resolving the gesture, BLE fast-mode, idle-input and peer-sync seams; deriving RAM fields without direct literal evidence; validating function arguments, stack/register contracts, branch targets, data-table semantics, flash capacity and heap reservation; then inspecting emitted calls and replaying the patch recipe. Any resulting candidate must be manually tested before CFW publication, per the existing testing gate.

Reproduce the comparison with `python3 scripts/cfw/compare_2_2_10_to_2_3_0.py` (Capstone required). The script validates the existing profile against its original stock images before comparing the new image. Full evidence is in `2.2.10-to-2.3.0-address-comparison.json`. It performs no firmware build, profile mutation or device access.
